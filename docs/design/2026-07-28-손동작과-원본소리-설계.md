# 손동작 확장과 원본 분포 기반 파편 선택 — 설계

> **이후 경과:** 1번(손 모양을 도구로)은 만들어서 돌려 본 뒤 되돌렸다.
> 손 모양을 신경 쓰기 시작하면 ASMR이 아니라 조작이 된다. 손바닥 모드는 다시
> "손에 올려놓고 쥐면 부서진다" 하나다. 2·3·4번(손 위 물리감, 목표와 연출,
> 파편 선택)은 그대로 남아 있다.

## 왜 하는가

손바닥 모드가 심심하다. 이유는 구조에 있다.

- **동작이 하나뿐이다.** 손을 쥐면 부서진다, 끝이다. 실제로 왁뿌볼을 갖고 놀 때 하는
  손톱으로 뜯기·긁기가 없다.
- **도구 5종을 하나도 안 쓴다.** 손바닥 모드는 `pressArea`만 부른다.
- **어딜 만져도 똑같이 부서진다.** 접촉 방향으로 늘 `FACING`(정면)에 `cos = -1`(구 전체)을
  넘기고 있어서, 손끝이 어디에 있든 구가 통째로 눌린다.
- **부스러기가 그냥 사라진다.** 손바닥 모드의 바닥 높이는 화면 밖이다.
- **볼이 손 위에 "놓여" 있지 않다.** 화면 좌표만 따라다녀서 손을 기울여도 볼은 가만히 있다.

소리 쪽에도 남은 것이 하나 있다. 파편을 고르는 기준이 노이즈 합성 시절 유물이라
녹음보다 어두운 파편이 계속 뽑힌다.

## 무엇을 만드는가

네 덩어리다. 파괴 모델(`BreakModel`)과 소리 합성기의 뿌리는 구조는 건드리지 않는다.
전부 기존 API 위에 얹는다.

### 1. 손 모양이 곧 도구다

새 파일 `ar/HandGesture.kt`. `HandLandmarks` 하나를 받아 손 모양을 판정한다.
안드로이드 API를 안 쓰므로 PC에서 전부 검증한다.

| 손 모양 | 판정 | 동작 | 도구 |
|---|---|---|---|
| 얹힘 | curl < 0.15 | 파괴 없음 | — |
| 집기 | 엄지끝↔검지끝 < 손폭 × 0.35 | 집은 자리만 뜯김 | `NAIL` |
| 긁기 | curl 0.2~0.7 이고 검지 끝이 손바닥 기준으로 초당 손폭 1.2배 이상 이동 | 지나간 자리가 얕게 까임 + 마찰음 | `FINGER` |
| 쥐기 | curl이 증가하는 중 | 구 전체 압착 | `FIST` |

우선순위는 집기 > 긁기 > 쥐기 > 얹힘.

접촉 지점은 제스처마다 다르다. 집기는 엄지 끝과 검지 끝의 중점, 긁기는 검지 끝,
쥐기는 지금처럼 구 전체(`contactCos = -1`)다. 쥐면 손가락이 볼을 감싸므로 뒷면까지
으스러지는 것이 맞다.

**히스테리시스가 필수다.** 바뀌려면 3프레임 연속 같은 판정이 나와야 하고, 한번 잡히면
5프레임 어긋나야 풀린다. 인식은 프레임마다 떨리므로, 이게 없으면 도구가 매 프레임 바뀐다.
판정이 애매하면 이전 제스처를 유지한다. 도구가 없어지는 것보다 낫다.

**접촉 지점을 손끝에서 뽑는 것이 이 덩어리의 핵심이다.** 손끝 화면 좌표를
`renderer.screenToRayFor(index, x, y, ray)` → `Picker.hitDirection(origin, dir)` 로
구면 방향으로 바꿔 `pressArea`에 넘긴다. 일반 모드가 손가락 터치를 처리하는 경로와 같다.

`screenToRay`는 볼이 원점에 있다고 가정한다. 손바닥 모드는 볼을 세계 좌표로 옮겨
놓으므로(`offsetX/Y/Z`), 그 오프셋을 빼는 `screenToRayFor(index, …)` 를 따로 만든다.

찍는 도구(`continuous = false`)는 손 모양이 막 바뀐 프레임에만 `strikeArea`로 들어간다.
문지르는 동안 계속 먹히면 손맛이 사라진다. 일반 모드와 같은 규칙이다.

### 2. 손 위 물리감

새 파일 `ar/PalmPhysics.kt`. 역시 순수 Kotlin.

- **기울기**: `INDEX_MCP → PINKY_MCP` 벡터의 화면 각도로 손바닥 롤을 잰다.
  2D 랜드마크에서 안정적으로 나오는 유일한 자세 신호다. 앞뒤 기울기는 손 길이 대 폭
  비율로 추정할 수 있지만 오검출이 심해서 쓰지 않는다.
- **구름**: 롤에 비례해 볼이 낮은 쪽으로 굴러간다. 렌더러의 `ballRotation`을 그만큼 돌리고
  배치 좌표도 같은 방향으로 민다. 손 위 공들은 같은 손바닥에 있으므로 회전 하나를 공유한다.
- **쌓임**: 부스러기 바닥을 손바닥 평면 바로 아래로 올린다. 기울인 쪽으로 미끄러지고,
  공 전체를 합쳐 60개를 넘으면 오래된 것부터 낮은 쪽 가장자리로 흘러넘쳐 사라진다.
  `Debris`의 `hang`·`floorY`를 그대로 쓴다.

### 3. 목표와 연출

새 파일 `ar/ArSession.kt`. 순수 Kotlin.

- **콤보**: 1.2초 안에 다음 파괴가 이어지면 유지. 화면 구석에 작게 띄운다.
  콤보가 높아지면 화면 가장자리 글로우만 진해진다. **소리는 건드리지 않는다.**
- **슬로모션**: `areaFrac ≥ 0.03` 인 큰 판이 떨어지면 0.35초 동안 렌더 타임스케일 0.35배.
  **소리 피치는 그대로 둔다.** 소리가 전부인 앱이라 여기서 변조하면 안 된다.
- **기록**: 볼 하나를 다 까는 데 걸린 시간과 최고 콤보. 최고 기록만 저장한다.

기존 `Mission` 시스템은 건드리지 않는다. 손바닥 모드 전용 미션까지 넣으면 UI·판정·보상
배선이 붙는데, 볼 하나 클리어 타임 하나로 목표는 충분하다.

### 4. 원본 분포 그대로 파편 고르기

지금 파편을 고르는 기준은 노이즈 시절 유물이다. `randomFreq()` 가 `SKEW = 0.42` 만큼
아래로 치우친 목표 Hz를 던지는데, 이 값은 **노이즈 합성**의 중심 주파수를 녹음에
맞추려고 넣은 것이다. 파편은 이미 녹음의 스펙트럼을 갖고 있으므로, 여기에 같은 치우침을
걸면 어두운 파편만 계속 뽑혀 원본보다 둔해진다.

- `GrainBank.pickByRank(rank01, spread, rnd)` 를 추가한다. 절대 Hz가 아니라
  **밝기 순위(백분위)** 로 고른다. 뱅크는 이미 밝기 순으로 정렬돼 있다.
- 기본값 `rank01 = 0.5`, `spread` 는 전체의 ±35%. 이러면 뽑히는 파편의 밝기 분포가
  뱅크 분포, 곧 녹음 분포와 같아진다.
- 게임적 의미만 순위를 민다. 큰 조각 −0.2, 도구 밝기 ±0.15,
  재질은 `SoundProfile.brightnessRank` 필드를 새로 둔다.
- `randomFreq()` 는 노이즈 합성 경로(뱅크를 못 읽었을 때)에만 남긴다.

## 구조

**새로 만드는 것** — 전부 순수 Kotlin, PC에서 검증

| 파일 | 하는 일 | 의존 |
|---|---|---|
| `ar/HandGesture.kt` | 손 모양 판정 + 히스테리시스 | `HandLandmarks` |
| `ar/PalmPhysics.kt` | 손바닥 롤 → 볼 구름·부스러기 미끄러짐 | 없음 |
| `ar/ArSession.kt` | 콤보, 클리어 타임, 최고 기록 | 없음 |

**고치는 것**

| 파일 | 무엇을 |
|---|---|
| `ar/PalmPose.kt` | 롤, 손끝 좌표, 손끝 속도를 내보낸다 |
| `ar/ArPlayActivity.kt` | 위의 것들을 엮는 배선. 판단 로직은 넣지 않는다 |
| `gl/BallRenderer.kt` | `screenToRayFor(index, …)`, 렌더 타임스케일 |
| `audio/GrainBank.kt` | `pickByRank` |
| `audio/Synth.kt` | 파편 경로는 순위로 고른다 |
| `core/SoundProfile.kt` | `brightnessRank` |

경계는 지금과 같다. `ar/` 의 계산 클래스들은 안드로이드 API를 모르고, `ArPlayActivity`는
손 좌표를 그 클래스들에 넘기고 결과를 기존 파괴·소리 API로 옮기는 일만 한다.

## 데이터 흐름

```
카메라 프레임
  → HandTracker (MediaPipe)      : 관절 21개
  → PalmPose                     : 손 중심 · 손 폭 · 쥔 정도 · 롤 · 손끝 좌표/속도
  → HandGesture                  : 얹힘 / 집기 / 긁기 / 쥐기  (히스테리시스 통과 후)
  → ArPlayActivity
        · 제스처 → Weapon
        · 손끝 좌표 → screenToRayFor → Picker.hitDirection → 구면 방향
        · BreakModel.pressArea / strikeArea
  → EventQueue → Synth → GrainBank.pickByRank → SampleGrainPool
PalmPhysics : 롤 → ballRotation, 부스러기 미끄러짐
ArSession   : 파괴 이벤트 → 콤보 · 클리어 타임
```

## 실패 처리

- **손을 놓치면** 제스처는 즉시 풀리고 힘이 끊긴다. 볼과 부스러기는 마지막 자리에 남는다.
  지금 동작 그대로다. 볼이 사라지거나 튀면 거슬린다.
- **판정이 애매하면** 이전 제스처를 유지한다.
- **손 위 부스러기가 60개(공 전체 합산)를 넘으면** 오래된 것부터 낮은 쪽으로 흘러넘쳐
  사라진다. 무한정 쌓이면 프레임이 죽는다.
- **뱅크를 못 읽으면** 지금처럼 노이즈 합성으로 되돌아간다. 이때는 `randomFreq()` 경로를 쓴다.

## 테스트

전부 PC에서 도는 JVM 테스트다. 카메라도 기기도 필요 없다.

| 무엇을 | 어떻게 |
|---|---|
| 제스처 분류 | 네 가지 손 모양의 좌표를 만들어 각각 옳게 나오는지 |
| 히스테리시스 | 두 판정 사이를 떨리는 입력을 넣어 도구가 안 바뀌는지 |
| 접촉 지점 | 손끝을 볼 왼쪽에 두면 왼쪽 조각이, 오른쪽에 두면 오른쪽 조각이 깨지는지 |
| 기울기 → 구름 | 롤 부호에 따라 구르는 방향이 뒤집히는지 |
| 부스러기 | 기울인 쪽으로 미끄러지는지, 상한을 넘으면 사라지는지 |
| 콤보 | 1.2초 안에 이어지면 유지되고 넘으면 끊기는지 |
| 파편 순위 분포 | 기본 설정으로 2000번 뽑아 중앙값·사분위가 뱅크 전체와 ±10% 안인지 |

파편 순위 테스트는 지금 방식이 어느 쪽으로 얼마나 치우쳤는지도 같은 보고서에 남긴다.
그래야 바꾼 것이 실제로 효과가 있었는지 숫자로 보인다.

## 하지 않는 것

- **두 손 상호작용.** 인식기는 두 손을 잡고 있지만 큰 손 하나만 쓴다. 지금 구조를 유지한다.
- **손 관절 21개 전부를 충돌체로.** MediaPipe의 z는 상대 깊이라 신뢰도가 낮다. 2D 좌표로
  3D 충돌을 만들면 오검출이 심하고, 구면 기반인 `BreakModel`을 갈아엎어야 한다.
- **손바닥 모드 전용 미션.** 클리어 타임 하나로 대신한다.
- **앞뒤 기울기(피치) 추정.** 롤만 쓴다.
- **콤보에 따른 소리 변조.** 소리는 녹음에 충실해야 한다.
