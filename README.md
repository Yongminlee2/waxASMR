# 왁뿌볼 ASMR

왁스 뿌시기 볼을 화면에서 굴리고 문질러 까면서, 그때 나는 "빠자자작" 소리를 듣는
안드로이드 촉감·ASMR 앱.

성공 기준은 하나다. **눈 감고 소리만 들었을 때 진짜 왁뿌볼 부수는 소리로 들려야 한다.**
그래픽·미션·수집은 전부 그 소리를 계속 듣게 만들기 위한 장치다.

---

## 무엇을 하는 앱인가

3D 왁스볼을 손가락으로 만지면 그 자리가 깨진다. 세게 누르면 깊게, 쭉 문지르면 줄줄이.
금은 옆 조각으로 번지고, 떨어진 조각은 바닥에 쌓인다. 껍질을 다 벗기면 안쪽 말랑이가
드러나고, 가운데에서 도감 아이템이 나온다.

- **샌드박스** — 목표도 점수도 없다. 다 까면 새 볼이 굴러온다. 이게 본체다
- **미션** — 매일 3개. 속도·한 획·정밀·사방·콤보·껍질만
- **도감** — 볼 30종. 완파하면 안에서 나온 아이템과 소리 설명이 채워진다

## 조작

| 동작 | 결과 |
|---|---|
| 볼 위 한 손가락 탭 | 그 지점 깨기 |
| 볼 위 길게 누르기 | 힘이 쌓이며 연속 크랙 |
| 볼 위 드래그 | 지나간 자리가 줄줄이 까임 |
| 볼 **바깥** 여백 드래그 | 볼 굴리기 |
| 두 손가락 드래그 | 어디서든 굴리기 |
| 핀치 | 확대·축소 |
| 바닥의 부스러기 문지르기 | 더 잘게 부수기 |

### 손바닥에 올리기 (AR)

카메라로 손바닥을 비추면 그 위에 볼이 올라오고, **손을 쥐면 쥔 만큼 부서진다.**
실제 왁뿌볼을 쥐는 동작 그대로다.

| 동작 | 결과 |
|---|---|
| 손바닥을 펴서 비추기 | 그 위에 볼이 올라온다 |
| 손을 쥐기 | 쥔 세기만큼 볼 전체가 으스러진다 |
| 아래 색동그라미 | 카메라를 켠 채로 볼 종류를 바꾼다 |
| "공 N개" 버튼 | 손 위에 올릴 개수를 1~3으로 바꾼다 |

손을 놓치면 볼을 감추고 안내를 띄운다. 카메라 권한이 없거나 인식 모델을 못 읽으면
안내하고 기존 모드로 돌려보낸다. AR을 강요하지 않는다.

### 뿌시는 도구

손가락 하나로만 문지르면 어떻게 만져도 똑같이 깨져서 금방 지루해진다.
플레이 화면 아래에서 언제든 바꿀 수 있다.

| 도구 | 성격 |
|---|---|
| 👆 손가락 | 쭉 문질러 넓게. 기본 |
| 💅 손톱 | 한 조각씩 콕콕. 좁고 깊게 파인다 |
| 🔨 망치 | 한 방에 우수수. **찍을 때만** 들어간다 |
| 🌀 드릴 | 대고 있으면 계속 갈려 나간다 |
| ✊ 주먹 | 가장 넓게 뭉갠다. 둔탁하게 |

닿는 넓이·힘·화면 흔들림·진동 세기·음색이 전부 다르다.
망치와 주먹은 문지르는 동안 계속 먹히지 않아서, 내려칠 때마다 한 방씩 터진다.

깨기와 굴리기가 서로 먹지 않게 볼 안/밖으로 영역을 나눴다. 그래도 헷갈리면
우측 하단 "굴리기 잠금"을 켜면 화면 전체가 깨기 영역이 된다.

## 소리를 어떻게 만들었나

**실제 왁뿌볼을 녹음해 파열음 하나하나를 잘라 쓴다.** 다만 그걸 통째로 재생하지는 않는다.

처음에는 노이즈를 필터에 통과시켜 합성했다. 수치는 녹음에 맞출 수 있었지만
왁스 특유의 음색이 끝내 나오지 않았다. 반대로 녹음을 통으로 재생하면 몇 번만 들어도
같은 소리인 게 귀에 잡히고, 손가락 힘에 따라 변하지도 못한다.

그래서 **파편을 잘라 흩뿌리는 방식**으로 갔다. 진짜 소리를 쓰면서도 반복이 안 들린다.

### 파편 만들기 (개발 단계)

```
녹음 → 파열 검출 → 하나하나 잘라내기(22~240ms, 여운까지)
    → 잡음·지속음 걸러내기 → 녹음 전체 기준 한 번만 정규화 → 밝기 순 정렬
    → assets/grains.bin + grains.idx
```

현재 뱅크는 60초 녹음에서 **파편 405개**(6.9MB). 검출한 파열 491개 중 82%를 건졌다.

잘라낼 때 버린 것은 이유별로 세어 보고서에 남긴다. 한번은 목소리를 걸러내려고 둔
어택 조건이 멀쩡한 파편까지 쳐내서 491개 중 404개를 버린 적이 있는데,
그때는 숫자를 안 세고 있어서 한참 뒤에야 알았다.

### 파편 흩뿌리기 (실시간)

```
파괴 이벤트 1개 = 파편 1~3개를 26ms 안팎 간격으로 겹침
  · 목표 밝기에 가까운 파편들 중에서 무작위로 고름
  · 고를 때마다 재생 속도를 ±1반음 안에서만 흔듦
  · 파편은 끝까지 튼다 (여운을 자르지 않는다)
  · 좌우 위치는 손가락을 따라감
```

파편 뱅크를 못 읽으면 예전 노이즈 합성으로 되돌아간다. 소리가 아예 안 나는 것보다는 낫다.
그쪽 경로에서는 그레인 하나가 미세 파열이라, 지수분포 간격으로 수십 개를 뿌려야
파열음 하나가 만들어진다. 간격을 균등하게 두면 기계음이 된다.

### 원본을 통째로 튼 것이 더 나았던 이유

비교용으로 녹음을 그대로 재생하는 스위치를 넣어 봤더니(설정 → "녹음 원본 그대로 재생")
**원본 쪽이 더 왁뿌볼 같았다.** 파편으로 쪼개는 과정에서 세 가지를 망가뜨리고 있었다.

| 망가뜨린 것 | 어떻게 들렸나 | 고친 방법 |
|---|---|---|
| 파편마다 따로 최대 음량으로 정규화 | 작게 바스락거리는 것도 큰 파열만큼 커져서 전부 균일하게 시끄러움 | 녹음 전체 최고점으로 한 번만 나눔 |
| 다음 파열 직전에서 자르고, 재생할 때 감쇠값(12~36ms)으로 또 자름 | 앞머리만 남아 딱딱하고 메마름 | 여운 90ms까지 물고 오고, 재생할 때는 끝까지 틈 |
| 재생 속도를 ±3반음까지 흔듦 | 왁스가 아닌 다른 재질처럼 들림 | ±1반음 |

**자를 때 쓰는 판정은 앞머리 80ms만 본다.** 여운을 물고 오게 바꾸자마자
"어택이 느리다"는 이유로 176개가 버려졌는데, 파편 뒤쪽에 물려 온 더 큰 파열이
최고점으로 잡혀서 앞의 멀쩡한 파열이 느리다고 오판된 것이었다.
필터가 보려던 것은 앞머리이므로 앞머리만 본다.

### 파편은 밝기 순위로 고른다

여기에 유물이 하나 더 있었다. 파편을 고르는 목표 주파수에 노이즈 시절의 치우침(SKEW)이
그대로 걸려 있었다. 그 값은 필터를 통과한 노이즈의 스펙트럼 중심을 녹음에 맞추려고
넣은 것인데, 파편은 이미 녹음의 스펙트럼이라 거기 같은 치우침을 걸면 어두운 파편만
계속 뽑힌다. 재 보니 **뽑히는 파편의 밝기 중앙값이 1797Hz, 뱅크(=녹음)의 중앙값은
2781Hz**였다. 35% 어두운 소리만 듣고 있었던 셈이다.

절대 주파수 대신 **뱅크 안의 밝기 순위(백분위)** 로 고르도록 바꿨다.
그러면 뽑히는 분포가 곧 녹음의 분포가 된다. 재질 차이는 순위를 미는 것으로 준다
(`SoundProfile.brightnessRank`). 큰 조각은 어둡게, 밝은 도구는 밝게.
`randomFreq()` 는 뱅크를 못 읽었을 때의 노이즈 합성 경로에만 남는다.

바꾸자마자 회귀 테스트가 걸렸다. 밝은 파편은 원본에서 더 큰 파열이라 전체 레벨이
올라갔고, 리미터가 피크를 깎아 크레스트가 무너졌다(무른 왁스 11.1 → 8.2).
파편 진폭을 0.62에서 0.30으로 내리고, 뱅크의 가장 어두운 끝까지 파고들던 재질 둘의
순위를 올렸다. 지금은 굳은 왁스 12.1 · 저역 12%, 무른 왁스 10.7 · 12%,
설탕유리 11.8 · 10%, 큰 조각 분리 22.8 · 13% 다. 녹음은 13.8 · 12%.

### 손가락 힘이 소리를 바꾼다

| 행동 | 결과 |
|---|---|
| 살살 탭 | 파편 적게, 성기게 |
| 꾹 누르기 | 파편 많이, 촘촘하게 |
| 문지르기 | 속도에 비례해 계속 방출 |
| 큰 조각 분리 | 낮고 여운이 긴 "뽀각" 뒤에 밝은 부스러기가 뒤따른다 |
| 코어 누르기 | 크랙 없이 220~480Hz 마찰음만. 어택 7ms로 둔하게 |
| 도구 바꾸기 | 쇠붙이는 밝은 파편, 뭉툭한 것은 둔한 파편을 고른다 |

### 파편 하나가 곧 파열 하나다

노이즈로 합성하던 시절에는 그레인 하나가 "미세 파열"이라, 수십 개를 불규칙하게
흩뿌려야 파열음 하나가 만들어졌다. 그래서 크랙 한 번에 수십 개를 뿌리는 스케줄러를 뒀다.

녹음 파편으로 바꾸면서 **그 스케줄러를 그대로 뒀다.** 그런데 잘라낸 파편은
이미 완성된 파열음 하나다. 크랙 한 번에 **67개**를 뿌리고 있었고, 파열이
예순일곱 겹으로 쌓이니 왁스가 아니라 자갈이 쏟아지는 소리가 났다.

파편 방식에서는 크랙 한 번에 **최대 세 개**만 겹친다. 조각이 떨어질 때도
분리음 하나에 부스러기 한둘을 덧붙이는 정도다. 문지르는 소리와 착지음은 하나씩만 얹는다.

### 소리 측정은 실제 출시 경로를 재야 한다

이 문제를 한참 못 찾은 이유가 있다. **소리 측정이 전부 노이즈 합성 경로를 재고 있었다.**
파편 뱅크는 assets에 있어서 PC 테스트에서 못 읽었고, 그래서 테스트가 만드는 합성기는
항상 노이즈로 떨어졌다. 실제로 출시되는 것은 파편 재생 경로인데 거기에 측정이 없었다.

뱅크 파일은 그냥 파일이므로 PC에서도 직접 읽으면 된다. 그렇게 바꾸고 나서야
크랙 한 번에 67개를 뿌린다는 것이 숫자로 보였다.

### 시원함과 깊이감은 잴 수 있다

같은 종류의 앱이 업데이트로 소리를 바꿨다가 "터뜨리는 맛이 없어졌다",
"시원한 소리가 없다", "깊이감이 없어졌다"는 평을 받은 사례가 있다.
셋 다 감상평 같지만 수치로 잴 수 있다.

- **시원함 = 크레스트**(피크 ÷ 실효값). 순간적으로 확 솟는 정도.
  리미터가 세게 걸리거나 저역이 계속 깔리면 이 값이 무너지고 소리가 납작해진다
- **깊이감 = 저역 비중.** 많다고 좋은 게 아니다. 과하면 웅웅거려 오히려 시원함이 죽는다

실제 녹음이 기준이다. **크레스트 13.8, 저역 12%.**

처음에는 저역을 과하게 넣었다가 무른 왁스가 저역 43%, 크레스트 9.4까지 떨어졌다.
저역을 절반 이하로 줄이자 크레스트가 15.6까지 올라왔다. 깊이감은 저역을 많이 넣는
것이 아니라 **한 방이 묵직하게 꽂히는 것**이었다.

| | 고치기 전 | 고친 뒤 | 녹음 |
|---|---|---|---|
| 굳은 왁스 크레스트 | 11.2 | **15.6** | 13.8 |
| 굳은 왁스 저역 | 29% | **15%** | 12% |
| 무른 왁스 크레스트 | 9.4 | **11.8** | 13.8 |
| 무른 왁스 저역 | 43% | **22%** | 12% |

이 값들은 회귀 테스트로 잠가 뒀다. 소리는 코드를 조금만 건드려도 조용히 납작해지는데,
귀로만 확인하면 알아채기 어렵다.

파편의 여운을 살리고 정규화를 걷어낸 뒤 다시 재면 **굳은 왁스 크레스트 10.3 · 저역 11%,
무른 왁스 11.1 · 12%, 큰 조각 분리 15.6 · 8%** 이다. 저역 비중은 녹음(12%)과 거의 같아졌고,
크레스트는 파편이 끝까지 울리는 만큼 실효값이 올라가 조금 내려갔다.

### 한 번 부술 때 소리는 하나다

손가락이 닿는 넓이만큼 한꺼번에 깨지다 보니, 한 프레임에 조각 여섯 개가 동시에
떨어지는 일이 생긴다. 조각마다 분리음을 따로 내면 저역이 여섯 겹으로 쌓여 뭉쳐 울린다.

그래서 한 번 누를 때 떨어진 조각을 모아 **넓이를 합친 분리음 하나**로 낸다.
넓이에는 상한을 둬서 연쇄로 한꺼번에 많이 떨어져도 저역이 폭주하지 않는다.
깨지는 양은 그대로고 소리만 묶는다.

### 실측으로 잡은 값

직접 녹음한 왁뿌볼 영상 세 개를 분석해 프로파일을 다시 잡았다. 감으로 잡았던 처음 값은
네 가지가 크게 틀렸다.

| | 처음 (감) | 녹음 실측 |
|---|---|---|
| 음높이 산포 | 0.8 옥타브 | **1.5~2.1 옥타브** |
| 파열 간격 | 1.2~6ms | **81~208ms (귀에 들리는 단위)** |
| 저역 비중 | 0% | **6~21%** |
| 평탄도 | 잡음에 가까움 | **0.18~0.31 (음정이 있는 쪽)** |

종류가 다른 세 개라 재질별 성격도 추측이 아니라 실측으로 나눌 수 있었다.
왁뿌볼2는 성기고(간격 208ms) 음정감이 가장 강했고(0.18), 왁뿌볼3은 압도적으로 밝았다
(중심 6253Hz, 고역 74%).

**주의**: 녹음에는 폰 마이크 특성·방 울림·AAC 압축이 섞여 있다. 스펙트럼 수치를 1:1로
맞추려 들면 마이크를 흉내 내게 된다. 큰 방향(파열 밀도, 산포, 저역 유무, 음정감)까지만
수치로 맞추고 나머지는 귀로 판단한다.

### 실제 녹음에서 파라미터 뽑기

귀로 "좀 더 낮게"를 반복하는 것보다 정답지의 수치를 재서 맞추는 편이 빠르다.
실제 왁뿌볼을 녹음한 WAV를 `app/reference/` 에 넣고 `test.bat`을 돌리면
파열 빈도·간격·스펙트럼 중심·산포·감쇠 시간·대역 분포·평탄도를 재서,
그대로 붙여 넣을 수 있는 `SoundProfile` 초안을 `app/build/reference-report.txt` 에 써 준다.

분석기 자체는 정답을 아는 합성 신호(간격 60ms·2kHz 클릭 열 등)로 검증한다.
녹음이 없으면 이 단계는 조용히 건너뛴다.

### 재질 5종

파편을 고르는 기준 주파수다. 녹음의 스펙트럼 중심이 3107Hz였으므로,
기본 볼은 거기에 맞춰야 녹음에 실제로 들어 있는 소리가 나온다.
임의로 다른 값을 주면 뱅크 한쪽 끝의 파편만 골라서 녹음과 다른 소리가 된다.

| 재질 | 기준 주파수 | 성격 |
|---|---|---|
| 굳은 왁스 | 3107Hz | 녹음 실측값 그대로. 기본 볼(노른자) |
| 무른 왁스 | 2600Hz | 조금 낮은 쪽 파편. 기본 볼(찹쌀떡) |
| 알갱이 왁스 | 2400Hz | 파열이 가장 촘촘하다 |
| 반짝이 왁스 | 3600Hz | 자잘하고 밝은 사각사각 |
| 설탕 유리 | 4300Hz | 가장 밝고 여운이 길다 |

여기에 크기(주파수·여운), 두께(밝기·감쇠·공명), 모양(전파·공명·산포)이 곱해져
볼 30종이 **전부 다른 소리**를 낸다.

### 스테레오와 지연

터치 x좌표가 그대로 팬이 된다. 이어폰을 끼면 손가락을 따라 소리가 좌우로 움직인다.
ASMR에서 공간감은 음색만큼 중요하다.

지연 목표는 **30ms 이하**. 손가락과 소리가 어긋나면 뇌가 가짜로 인식해서
효과가 통째로 사라진다. 기기 네이티브 샘플레이트·버퍼를 그대로 쓰고,
`AudioTrack`을 `PERFORMANCE_MODE_LOW_LATENCY` + `PCM_FLOAT`로 연다.

**오디오 스레드에서는 객체를 하나도 만들지 않는다.** 그레인 상태는 전부 사전 할당된
원시 배열이고, 파괴 이벤트도 객체가 아니라 링 버퍼의 한 줄로 넘긴다.
GC가 오디오 콜백을 한 번 멈추면 소리가 뚝 끊긴다.

### 조각을 어떻게 나누나

구면을 직접 자르지 않는다. 세분화된 구 메시(5120삼각형)의 각 삼각형을 가장 가까운
시드에 배정해 군집을 만든다. 격자 무늬가 생기지 않고 축퇴 폴리곤 같은 기하 예외가
원천적으로 없다. **시드는 매번 새로 뽑기 때문에 같은 볼을 두 번 깨도 갈라지는 모양이 다르다.**

### 금은 어떻게 그리나

별도 텍스처를 쓰지 않는다. 금이 갈수록 조각을 자기 중심 쪽으로 0~3% 줄인다.
조각 사이에 틈이 벌어지고, 그게 눈에는 금으로 보인다.

조각별 변환은 유니폼 배열 대신 **부동소수점 텍스처**로 넘긴다.
ES 3.0이 보장하는 유니폼 vec4 개수(224)로는 조각 300개를 못 담기 때문이다.

### 조각 크기를 왜 일부러 들쭉날쭉하게 만드나

시드를 고루 뿌리면 조각 크기가 죄다 비슷해진다. 그러면 어디를 깨도 같은 크기가
떨어지고, 크기가 같으니 되돌려 줄 반응도 매번 같을 수밖에 없다.
**넓은 판이 통째로 벗겨지는 순간이 아예 생기지 않는다.**

그래서 시드의 20%만 전체에 고루 뿌려 넓은 판을 만들고, 나머지는 몇 군데 좁은 구역에
몰아넣어 그 자리만 잘게 부서지게 한다. 보로노이 조각 크기는 시대 밀도에 반비례하므로
이것만으로 크기가 갈린다. 가장 큰 판이 중간 크기의 6배 이상 나온다.

한 볼 안에 넓은 판 3장 이상과 자잘한 부스러기 20개 이상이 함께 나오는지 테스트로 고정해 뒀다.

### 손을 볼로 바꾸는 법

**ARCore를 쓰지 않는다.** ARCore는 바닥·벽 같은 평면을 잡는 도구라 손은 못 본다.
손바닥 위에 올리려면 손 관절을 직접 인식해야 하므로 MediaPipe를 쓴다.
덕분에 별도 설치(Play 서비스 AR)도 필요 없어졌다.

- **자리** — 손목과 손가락뿌리 두 곳, 세 점의 평균이 손바닥 한가운데다.
  이 셋은 쥐어도 거의 안 움직인다. 손가락 끝을 쓰면 쥘 때마다 볼이 딸려 들어간다
- **크기** — 검지뿌리와 새끼뿌리 사이 거리가 손 너비다. 여기에 맞춘다
- **쥐는 세기** — 손목에서 손가락 끝까지의 거리를 뿌리까지의 거리로 나눈 비율.
  거리 비율이라 손이 멀어져도 안 흔들린다. 각도로 재면 손을 기울일 때마다 튄다
- **떨림** — 위치·크기·세기 전부 지수 평활을 건다. 없으면 볼이 계속 지글거리고,
  세기가 튀어서 쥐지도 않았는데 부서진다

### 쥔 채 가만히 있으면 힘이 0이다

쥐는 세기가 **늘어나는 동안에만** 힘을 준다. 계속 쥐고만 있어도 부서지면
조작하는 느낌이 사라진다. 쥐었다 폈다를 반복하는 것이 이 모드의 기본 동작이다.

힘은 세기 변화량을 시간으로 나눠 구하므로 프레임 속도가 달라져도 손맛이 같다.

### 쥐면 볼 전체가 으스러진다

처음에는 카메라 쪽 반구만 눌렀다. 그러면 앞쪽 뚜껑만 깨지고 가장자리가 멀쩡히
남아서, 손에 쥐는 게 아니라 파는 것처럼 보인다. 손가락은 볼을 감싸므로 뒷면까지
전부 대상이어야 한다. 닿는 세기만 앞쪽을 조금 강하게 남겼다.

### 볼 여러 개를 그리는 법

렌더러가 볼 하나만 들고 있으면 여러 개를 못 그린다. 하나를 두고 매 프레임 바꿔
올리면 그때마다 수십만 개 정점을 다시 보내야 해서 못 쓴다.
그래서 GL 버퍼와 텍스처를 **볼마다 따로** 들고 목록으로 관리한다.
일반 모드는 목록에 하나인 경우로 같은 경로를 탄다.

AR은 처음에 볼을 원점에 두고 카메라를 옮겨 손 위에 보이게 했다. 카메라가 하나뿐이라
공을 여러 자리에 놓을 수 없어서, 카메라를 고정하고 볼을 세계 좌표로 옮기도록 바꿨다.
셰이더가 위치에 배율을 곱하므로 옮길 거리는 배율로 나눠서 넣는다.

### 누르기와 때리기는 다른 것이다

문지르는 도구(손가락·손톱·드릴)는 `힘 × 시간`으로 손상이 쌓인다.
찍는 도구(망치·주먹)는 **정해진 충격량이 한꺼번에** 들어간다.

처음에는 찍는 것도 "한 프레임 동안 누르기"로 다뤘는데, 한 프레임 손상이
`힘 × 0.016초`라서 망치가 0.28밖에 못 넣었다. 조각이 떨어지는 임계가 0.76이니
간판 도구인 망치로 찍어도 계산상 아무 일도 일어날 수 없었다.

### 소리를 네 번 갈아엎었다

이 앱은 소리가 전부라서, 소리 방향을 잡는 데 가장 오래 걸렸다.

**1차 — 노이즈 합성.** 대역통과 필터를 통과시킨 노이즈를 그레인으로 흩뿌렸다.
설계상으로는 맞았고 손가락 힘에 따라 변하는 것도 됐지만, 들어 보니 왁스가 아니었다.

**2차 — 실측 기반 보정.** 실제 녹음을 분석해 파라미터를 맞췄다. 감으로 잡았던 값이
네 가지나 크게 틀렸다는 걸 알았다(산포 2.4배 좁음, 저역 0%, 파열 10배 촘촘, 잡음스러움).
수치는 녹음 범위 안으로 들어왔는데도 여전히 왁스 소리가 아니었다.
같은 분석기로 합성 결과를 되재면서 세 번 보정했지만, 마지막 두 번은 수치가 오히려 나빠졌다.

여기서 멈췄다. **녹음에는 마이크 특성과 방 울림이 섞여 있어서, 스펙트럼 수치를 1:1로
맞추려 들면 마이크를 흉내 내게 된다.** 노이즈 기반으로는 음색 자체가 안 나온다는 결론.

**3차 — 녹음 파편 재생.** 진짜 파열음을 잘라 쓰되, 뿌리는 구조는 그대로 뒀다.
이게 방향은 맞았다. 진짜 음색을 쓰면서도 매번 다른 파편·다른 간격이라 반복이 안 들린다.

**4차 — 원본과 맞대 보기.** 그런데도 소리가 안 맞아서, 비교용으로 녹음을 통째로 트는
스위치를 넣었다. 원본 쪽이 확실히 나았다. **뿌리는 구조가 아니라 파편을 만들고 트는
과정에서 원본을 망가뜨리고 있었다** — 파편마다 최대 음량으로 키워 셈여림을 지웠고,
여운을 두 번(자를 때 한 번, 틀 때 한 번) 깎아냈고, 피치를 ±3반음까지 밀었다.
셋 다 걷어내니 파편 쪽도 원본에 붙었다. 비교 스위치는 설정에 그대로 남겨 뒀다.

### 깨는 맛이 없다는 지적에서 나온 것들

소리가 잡히고 나니 "깨는 맛이 재미없고 지루하다"는 문제가 남았다.
원인을 파고들어 보니 셋으로 갈렸고, **뿌리는 조각 크기가 다 똑같은 것**이었다.

크기가 같으면 어디를 깨도 같은 크기가 떨어지고, 그러니 되돌려 줄 반응도 매번 같다.
큰 사건이 존재할 수 없는 구조였다. 크기를 벌린 뒤에야 나머지가 의미를 갖는다.

1. 조각 크기 다양화 (넓은 판 + 자잘한 부스러기)
2. 떨어진 넓이에 비례한 화면 흔들림과 진동
3. 떨어지기 직전 잠깐 매달리기
4. 넓은 판이 갈 때 들뜬 이웃을 데려가는 연쇄 붕괴
5. 바닥에 쌓인 부스러기를 문질러 더 잘게 부수기
6. 뿌시는 도구 5종

### 개발 중 잡은 문제와 원인

**빌드 환경**

- *Gradle 테스트 워커가 클래스를 못 찾음* — 사용자 홈 경로에 한글이 있어 클래스패스 인자
  파일이 UTF-8로 쓰이고 `java.exe`가 시스템 코드페이지로 읽었다. 정션을 걸어도 Gradle이
  실제 경로로 되돌려서 무용지물. ASCII 경로에 진짜 Gradle 홈을 따로 두어 해결
- *`.bat` 파일이 첫 줄부터 실패* — 주석을 한글로 썼더니 cmd가 파싱하지 못했다. ASCII로 교체
- *리소스 링크 실패 `attr/?? not found`* — 문자열 값 `???` 를 aapt가 테마 속성 참조로
  읽었다. `\?\?\?` 로 이스케이프
- *에뮬레이터가 뜨지 않음* — SDK 자체가 한글 경로에 있어 qemu 백엔드가 인자를 받지 못하고
  즉시 종료. SDK를 통째로 옮겨야 해서 실기기로 검증했다

**설계·구현**

- *볼 두 종의 소리가 완전히 겹침* — 모양이 소리에 반영되지 않아 노른자와 달걀이 같은
  프로파일이었다. 모양별로 금 전파·공명·음높이 산포를 부여해 30종 전부 구분되게 했다
- *코어 마찰음이 지나치게 밝음* — 어택이 0.4ms로 고정이라 저역 그레인에도 광대역 클릭이
  섞였다. 어택을 그레인 파라미터로 빼고 마찰음은 7ms로
- *볼이 화면 가로를 넘겨 잘림* — 카메라 거리를 세로 기준으로 잡아 세로 화면에서 좌우가
  잘렸다. 굴리기용 여백까지 사라졌다. 짧은 축의 82%에 맞추도록 수정
- *파열 하나를 두 번 셈* — 온셋 검출에 재무장 조건이 없어 간격이 절반으로 측정됐다.
  히스테리시스 추가
- *조용한 구간에서 잡음을 파열로 셈* — 이동 중앙값이 0으로 내려앉아 임계가 무너졌다.
  전역 하한 추가
- *한 번 부술 때 분리음이 여섯 개* — 붓 반경으로 여러 조각이 같이 임계를 넘는데
  조각마다 소리를 따로 냈다. 조각 크기를 다양화한 뒤로는 그중에 저역이 깊은 큰 판이
  섞이면서 뭉쳐 울렸다. 한 번 누를 때 떨어진 것을 묶어 소리 하나로 냈다
- *좋은 녹음의 82%를 버림* — 목소리를 걸러내려고 둔 어택 조건이, 여운이 긴 녹음에서
  앞 파열의 꼬리가 겹친 멀쩡한 파편까지 쳐냈다. 버리는 이유를 항목별로 세게 해서
  다시는 조용히 버려지지 않게 했다
- *3버튼 내비게이션 기기에서 UI가 시스템 바에 깔림* — targetSdk 36이라 화면 끝까지
  그려지는데 인셋을 처리하지 않았다. 제스처 내비 기기에서는 드러나지 않았다
- *망치와 주먹이 아무것도 못 깸* — 찍는 것을 "한 프레임 동안 누르기"로 다뤘더니
  손상이 `힘 × 0.016초`라 주먹 0.176, 망치 0.28이 들어갔다. 조각이 떨어지는 임계가
  0.76이니 계산상 아무 일도 일어날 수 없었다. 타격을 시간과 무관한 충격량으로 분리
- *부스러기가 하단 바에 묻힘* — 바닥이 화면 아래 끝에서 0.27밖에 안 떨어져 있어
  도구 줄과 버튼에 가렸다. 문질러 뭉개는 조작 자체가 불가능했다
- *조작법 안내가 매번 다시 뜸* — 안내가 저장소를 새로 읽어 플래그를 켜고 저장하는데,
  플레이 화면이 나갈 때 자기 사본을 저장하면서 그 플래그를 도로 지웠다
- *쥐는 힘이 30배 작았음* — 배율을 0.075로 잡았는데 실제로 나오는 힘이 0.077이었다.
  파괴 모델이 기대하는 범위는 1~4다. 눈으로 봤으면 "왜 안 부서지지"로 한참 헤맸을 값이다
- *쥐면 앞면만 부서짐* — 카메라 쪽 반구만 눌러서 앞쪽 뚜껑만 깨지고 가장자리가 남았다.
  손에 쥐는 게 아니라 파는 것처럼 보였다
- *APK가 60.6MB로 부풂* — 손 인식 라이브러리가 x86 20.5MB, armeabi-v7a 8.1MB를
  함께 실었다. x86은 에뮬레이터 전용이고 요즘 폰은 전부 arm64다. 31MB로 줄였다
- *진단 코드가 PNG를 2초마다 영구 저장* — 인식이 안 되는 원인을 찾으려고 넣은 것을
  끄지 않고 뒀다. 기본 꺼짐으로 바꿨다
- *왁스가 아니라 자갈 쏟아지는 소리가 남* — 노이즈 시절의 스케줄러를 그대로 두어
  크랙 한 번에 완성된 파열음 67개를 겹쳐 뿌리고 있었다
- *소리 측정이 안 쓰는 경로를 재고 있었음* — 뱅크를 PC에서 못 읽어 테스트가 항상
  노이즈 합성으로 떨어졌다. 실제 출시되는 파편 재생 경로에는 측정이 하나도 없었다

### 교훈

- **측정할 수 없는 것은 테스트하지 말 것.** 초당 800회 파열을 완성된 소리에서 되짚어 세는
  것은 신뢰할 수 없었다. 스케줄러가 정한 값을 직접 검증하는 쪽으로 바꾸니 명확해졌다
- **테스트가 틀릴 수도 있다.** 미션 테스트 3건이 실패했을 때 원인은 구현이 아니라 테스트
  설정이었다. 균열 전파 때문에 의도보다 많은 조각이 떨어졌고, 누르는 패턴이 실제 플레이와
  달랐다
- **예상과 반대인 측정값을 그대로 받아들일 것.** 큰 조각이 떨어질 때 여운이 앞머리보다
  밝게 측정됐다. 확인해 보니 낮은 "뽀각" 뒤에 밝은 부스러기가 따라오는 구조라 그게 맞는
  소리였다. 측정에 맞춰 테스트를 고쳤다
- **추측하기 전에 재 볼 것.** 소리가 뭉개진다는 지적에 원인을 두 번 짚었는데 둘 다 틀렸다.
  이벤트가 폭주하는 줄 알았지만 측정해 보니 정상 범위였고, 빈도가 과한 줄 알았지만
  실제 녹음 범위 안이었다. 세 번째로 한 프레임에 겹치는 분리음 수를 재고 나서야
  진짜 원인(여섯 개가 동시에 남)이 나왔다
- **버리는 것도 세어 둘 것.** 파편 추출에서 좋은 재료의 82%를 조용히 버리고 있었다.
  이유별로 세는 보고서를 붙이고 나서야 어느 조건이 범인인지 한눈에 보였다
- **기능을 넣었으면 그게 실제로 작동하는지 숫자로 확인할 것.** 도구 다섯 종을 넣고
  "다 됐다"고 넘길 뻔했는데, 균형을 재는 테스트를 쓰다가 망치와 주먹이 아무것도
  못 깬다는 걸 발견했다. 눈으로 봤으면 못 잡았을 버그다
- **원본과 맞대 볼 스위치를 만들어 둘 것.** 소리가 왜 안 맞는지 몇 번을 헤맸는데,
  녹음을 통째로 트는 스위치 하나를 넣자마자 "가공 과정이 문제"라는 답이 바로 나왔다.
  그 전까지는 뿌리는 구조를 계속 의심하고 있었다
- **전처리는 그때는 옳아 보인다.** 파편마다 음량을 맞추고 꼬리를 다듬고 피치를 맞추는 것은
  하나하나 다 그럴듯한 이유가 있었다. 셋이 겹쳐서 원본의 셈여림·여운·음색을 차례로
  지웠다는 건 원본과 나란히 듣고 나서야 알았다

## 빌드

```
build.bat      디버그 APK
test.bat       JVM 유닛테스트 188건
```

`build.bat`/`test.bat`은 `GRADLE_USER_HOME`을 ASCII 경로로 바꿔 준다.
사용자 홈 경로에 한글이 있으면 Gradle이 테스트 워커 클래스패스를 UTF-8로 쓰고
`java.exe`가 시스템 코드페이지로 읽어서 클래스패스가 깨진다.

- 요구: compileSdk 36 / minSdk 26, Android Studio 내장 JDK(jbr)
- 외부 의존성은 androidx·material·junit뿐. NDK도, 게임엔진도, 물리엔진도, 오디오 파일도 없다

## 검증

`test.bat`으로 도는 유닛테스트 188건이 파괴 규칙과 합성기 전체를 덮는다.

- 조각 분할: 삼각형 배정 누락·중복 없음, 인접 그래프 대칭, 빈 조각 없음
- 파괴: 상태 비가역성, 균열이 두 겹 밖으로 번지지 않음, 2만 회 무작위 입력 후 불변식 유지
- 합성: 클리핑 없음, DC 오프셋 없음, 재질별 스펙트럼 중심 분리, 같은 이벤트가 두 번 같지 않음
- 미션 6종 각각의 성공·실패 경계, 저장 손상 내성, 성능 등급 판정

`app/build/audition/`에 재질별·동작별 WAV가 매 테스트 실행마다 생성된다.
수치가 통과해도 진짜 왁뿌볼처럼 들리는지는 사람이 판단해야 하기 때문이다.

### 손 인식은 무엇을 검증하고 무엇을 못 하나

`PalmPose` 와 `ArLayout` 은 안드로이드 API를 쓰지 않는다. 손 관절 좌표를 직접 넣어
카메라 없이 검증한다. 이 두 곳이 손바닥 모드의 계산 전부다.

| 검증되는 것 | 방법 |
|---|---|
| 편 손 0, 주먹 1, 그 사이 단조 증가 | 관절 좌표를 단계별로 넣어 확인 |
| 쥘 때 볼이 딸려 들어가지 않음 | 편 손과 주먹의 중심 좌표 비교 |
| 쥔 채 가만히 있으면 힘 0 | 같은 손을 계속 넣어 힘 확인 |
| 한 프레임 튀어도 볼이 순간이동 안 함 | 좌표를 크게 튀게 한 뒤 출력 확인 |
| 공 여러 개가 겹치지 않고 손 안에 들어옴 | 개수별 거리·반지름 계산 |

카메라 인식 자체와 체감은 기기로만 확인된다.

### 검증 방식에 대해

이 앱은 눈으로 봐서는 맞는지 알 수 없는 것이 많다. 소리가 어떤지, 도구가 실제로
다르게 먹히는지, 파열이 얼마나 자주 나는지는 화면을 봐도 모른다.
그래서 **눈으로 못 보는 것은 전부 숫자로 재게 만들어 두었다.**

| 재는 것 | 도구 | 잡아낸 것 |
|---|---|---|
| 녹음의 파열 빈도·음높이·감쇠·대역 | `ReferenceAnalyzer` | 감으로 잡은 값이 네 가지나 틀림 |
| 합성 결과를 같은 잣대로 되재기 | 같은 분석기 | 설정 3400Hz인데 실제 5874Hz |
| 파편을 버리는 이유 | 추출 보고서 | 좋은 재료의 82%를 버리고 있었음 |
| 한 프레임에 겹치는 분리음 | 버스트 측정 | 여섯 개가 동시에 나 뭉쳐 울림 |
| 도구별 한 번 썼을 때 깨지는 양 | 균형 테스트 | 망치·주먹이 아무것도 못 깸 |
| 쥐는 힘이 실제로 얼마인지 | 손 계산 테스트 | 배율이 30배 작았음 |
| 소리의 크레스트와 저역 비중 | 녹음과 맞대 보기 | 저역 과다로 소리가 납작해져 있었음 |
| 크랙 한 번에 뿌리는 파편 수 | 스케줄러 값 직접 확인 | 67개를 뿌려 자갈 소리가 나고 있었음 |
| 초당 처리 프레임과 손 검출 횟수 | 인식 로그 | 어두운 화면을 재고 있어 판정이 안 되던 것 |

### 실기기 확인 결과 (Galaxy S20 Ultra, SM-G988N / Galaxy S24)

- **터치→소리 지연 8.4~12.2ms.** 목표 30ms를 크게 밑돈다.
  기기 네이티브 버퍼가 192프레임(4ms)이라 NDK 없이도 충분했다
  (`WaxBall` 태그로 로그에 찍힌다)
- 파편 뱅크 405개 정상 로드, 파편 재생 모드로 동작
- 파괴·금 번짐·조각 낙하·진동 모두 정상 동작
- 볼이 화면 가로를 넘겨 잘리던 문제 수정 — 짧은 축의 82%에 맞춰 카메라 거리를 잡는다
- 3버튼 내비게이션(S24)에서 UI가 시스템 바에 깔리던 문제 수정
- **렌더러를 볼 여러 개용으로 크게 고친 뒤에도 기존 모드에 회귀 없음.**
  볼 하나짜리 경로가 "목록에 하나"로 그대로 동작한다

아직 기기에서 못 본 것:

- **손바닥 모드 전체.** 카메라 앞에 손을 놓아야 확인되는데 그럴 방법이 없었다.
  손 인식이 되는지, 쥐면 부서지는지, 공 여러 개가 손 위에 흩어지는지 전부 미확인
- 볼 여러 개를 실제로 띄운 모습. 배치 계산은 테스트로 덮여 있지만 보이는 모습은 별개다

## 미해결 항목

- **파편 뱅크(`app/src/main/assets/grains.*`)는 저장소에 올리지 않는다.** 녹음 원본의
  출처가 정리되면 함께 올린다. 지금은 로컬 빌드에서만 소리가 난다
- **손 인식 모델(`app/src/main/assets/hand_landmarker.task`)도 올리지 않는다.**
  8MB짜리 이진 파일이라 저장소에 두지 않고 내려받아 넣는다.
  [모델 주소](https://storage.googleapis.com/mediapipe-models/hand_landmarker/hand_landmarker/float16/1/hand_landmarker.task)
- **손이 볼을 가리지 못한다.** 볼이 항상 손 위에 덧그려져서 "붙여놓은" 느낌이 난다.
  제대로 하려면 손 실루엣으로 가려내야 하는데 작업량이 몇 배가 된다
- **볼 여러 개는 실기기 미검증.** 배치 계산은 테스트로 덮여 있지만 보이는 모습은 별개다.
  기존 모드에 회귀가 없다는 것은 확인했다
- 손 인식이 어두운 방이나 빠른 움직임에서 얼마나 버티는지 미측정
- 카메라·인식·렌더를 동시에 돌릴 때 발열과 배터리 소모 미측정
- 코인은 미션 보상 기록으로만 남아 있고 쓸 곳이 없다
- 조각 300개(왕 크기)에서 60fps가 유지되는지 미측정
- 미션 6종의 난이도가 실제로 적당한지 미검증. 판정 로직은 테스트로 덮여 있지만
  "할 만한가"는 사람이 해 봐야 안다
- 도감 완파 기록이 여러 판에 걸쳐 제대로 쌓이는지 장시간 플레이 미검증
- 도구 5종이 손끝에서 실제로 다르게 느껴지는지는 사람이 만져 봐야 안다.
  수치상 다른 것은 테스트로 고정해 뒀지만 그게 재미로 이어지는지는 별개다
